= Split view MVP: implementation handoff

Status: implemented on `feature/split-view-mvp` (2026-11-10), working towards
https://github.com/qutebrowser/qutebrowser/issues/1716[issue #1716]. This is not
an upstream-approved design. The user has posted on the issue and intends to ask
on IRC. Incorporate maintainer feedback before locking in a public command API.
Read link:split-view-research.asciidoc[the research note] for source links and
the alternatives that were considered.

Two designs were built. This branch contains the light-touch one (*inspector
pane*). The other (*paired tabs*, see <<alternative,below>>) lives on
`feature/split-view-paired-tabs` so the two can be compared.

== Product contract

`:vsplit [url]` shows a second page to the right of the current page and
`:hsplit [url]` shows it below. The second page (the *pane*) is a split inside
the *same tab*, in the slot the tab's web inspector uses. It is not an extra
tab: no tab-bar entry, tab index or session entry.

* The pane is a full `AbstractTab`, so it can be browsed, scrolled, searched,
  and gets hints, zoom and history like any other page.
* Without a URL the pane loads the current page's URL (a fresh load, not a copy
  of the page's state or history). Calling `:vsplit`/`:hsplit` again moves the
  existing pane, and with a URL also navigates it.
* The two pages share the space equally, the divider can be dragged, and the
  ratio is kept on resize (the inspector keeps an absolute size instead).
* `:split-focus` switches focus between page and pane, `:split-close` closes the
  pane. Clicking a page focuses it. After a command line or prompt, and after
  leaving the tab and coming back, focus returns to the page which had it.

=== What "the focused page" means

"Focused page" is the pane if it has focus, otherwise the tab's own page
(`AbstractTab.active_pane()`). Every command falls into one of three groups:

*Follows the focused page.* Everything that works on page content or its URL:
`:open`, `:back`/`:forward`, `:reload`, `:stop`, scrolling, search, zoom, hints,
`:yank`, `:bookmark-add`, `:quickmark-save`, `:download`, `:view-source`,
`:edit-url`, `:navigate`, `:devtools`, `:fullscreen`, `:jseval`, userscripts
(`QUTE_URL`, `QUTE_TITLE`, the page handed to the script), the `{url}` and
`{title}` command variables, the status bar, and the back/forward indicator.
`:tab-clone` also clones the focused page, which is a handy way to pop the pane
out into its own tab.

*Always acts on the tab.* `:tab-close`, `:tab-pin`, `:tab-move` and the other tab
commands. Closing the tab closes its pane. `:tab-give` and `:tab-take` refuse
(unless `--keep`), because they would silently throw away one of the two pages.

*Always acts on the page, not the pane.* Marks (`m`, `'`), and anything which
calls `TabbedBrowser.load_url(newtab=False)` such as `:config-diff`. Marks mix
a URL with a scroll position and a later navigation, which makes "follow the
pane" more intrusive than it's worth, so they stay with the tab's own page.

== Design

A pane is created with `browsertab.create()` and put into the owning tab's
`InspectorSplitter`. State lives on the owner's `TabData`:

* `pane`: the pane tab (or `None`)
* `pane_active`: whether the pane has focus and is the command target
* `pane_owner` (on the pane tab): the tab it belongs to

`TabWidget` and the tab bar are untouched, so tab indices, tab commands and
session saving behave as before.

== Known limitations

* A tab can't have a pane and docked devtools at once (one shared slot). That
  includes devtools which were opened and then hidden. Both directions give an
  error.
* Panes are not saved in sessions and not restored by `:undo` (only the tab is).
* One pane per tab, no nesting.
* The pane has no tab-bar entry: it can't be selected, closed or moved there,
  and its load progress isn't shown there.
* Page-initiated full screen from the pane is not handled specially. The window
  goes full screen, but the pane is expected to fill only its own area. This is
  untested.
* Verified offscreen with QtWebEngine only; not on a real X11 or Wayland session
  and not with QtWebKit.

== Adversarial review

The first version claimed "page commands act on the focused page". Attacking
that claim, instead of testing the happy path, found that it was false in
several ways. All fixed, each with a test which was checked to fail without the
fix (the fix was removed and the scenario confirmed red):

* *`:tab-give` crashed.* It called `close_tab()` with the focused page, and with
  a pane focused that is the pane, which isn't in the tab bar. It also opened
  the page in the other window first. Now refused unless `--keep`.
* *URL based commands used the wrong page.* `:yank`, `:bookmark-add`,
  `:quickmark-save`, `:download`, `:edit-url`, `:navigate`, `{url}`, userscripts
  and the `:hint` base URL used the tab's URL while everything else used the
  pane. `:navigate up` computed a URL from the page and loaded it into the pane.
  `TabbedBrowser.current_url()` now follows the focused page; `{title}` and
  `QUTE_TITLE` use `current_title()`. Marks were pinned to the page explicitly.
* *The status bar could show the wrong tab.* Changing which view has focus
  emitted `current_tab_changed` even for a tab which isn't shown (for example a
  background tab's pane closing itself), and switching back to a tab whose pane
  had focus re-announced the page instead of the pane.
* *`InspectorSplitter.remove_pane()` corrupted a docked inspector* when called
  without a pane (found by a randomized test of the slot rules). Not reachable
  from the commands, but a public method shouldn't do that.
* The focus handler had no guard for shutdown, and the mode leaving was
  duplicated between tab and pane switches.

Also exercised (all pass): chaining `:vsplit ;; split-close ;; :vsplit`, quitting
with a pane open, opening and closing 15 panes in a row and checking no tab
objects stay registered, giving/taking tabs with panes, and a randomized test of
the pane/inspector slot rules with a model of the expected state.

== Decisions and trade-offs

Each entry gives the choice, the strongest case against it, and why it was kept
(or what is still unsettled).

*A pane is a full `AbstractTab`, not a bare web view.*
Against: it isn't a tab, yet it gets a tab id, a registry entry and
`TabData`, which blurs what "a tab" is. For: hints, search, zoom, history,
scrolling, downloads and the status bar all expect an `AbstractTab`; a bare
view would need a parallel implementation of each. Unsettled: whether upstream
wants to bless "a tab which isn't in the tab bar".

*`active_pane()` routing at a handful of call sites.*
Against: every future "current tab" lookup has to remember it, and this review
found several that had already forgotten (see above). For: the alternative of making
`TabWidget.currentWidget()` return the pane breaks the tab index identity
everything else relies on. Mitigation: the three groups above, and tests per
group. It remains the weakest point of the design.

*One global `QApplication.focusChanged` connection per window.*
Against: hidden global state, and it fires for every focus change in the
application. For: it returns early unless the current tab has a pane, and a
per-widget event filter doesn't work because QtWebEngine swaps its focus proxy
on navigation (the same reason `ChildEventFilter` exists for inspector clicks).

*Sharing the inspector's slot.*
Against: devtools and a pane exclude each other, including hidden devtools. For:
it reuses the splitter logic and persistence-free layout with no new widget
hierarchy. Alternative: nest another splitter; more code for a rare combination.

*`inspector.Position` for the pane's side.*
Against: the name is wrong for a pane. For: it is the type `InspectorSplitter`
already uses, and a new enum would be near-identical. A rename is cheap if
requested.

*`:vsplit` without a URL does a fresh load of the current URL.*
Against: can reload a page with side effects (POST results, one-time links). For:
simple and predictable, and `:tab-clone` already covers copying history.

*Refusing `:tab-give`/`:tab-take`.* Against: an error where it could "just work".
For: moving a tab with two pages means choosing which one survives, and silent
loss is worse than a message.

*No session persistence, no `:undo` of the pane.* Against: a saved layout is
lost. For: sessions would need a format and restore-order rules, which is where
the paired design spent most of its code. Easy to add later, hard to remove.

== Alternative: paired tabs

The original plan paired two *existing* tabs, each keeping its own tab-bar entry,
history and tab id, like Chrome does. `QTabWidget`'s page stack can only show one
page, so `TabWidget` has to stop using it. That is built on
`feature/split-view-paired-tabs`: a first commit makes `TabWidget` a facade over
a `ViewHost` splitter (tabs are never reparented), then pairs, commands, focus
and sessions on top.

Measured (production / tests / docs, lines added) when both were first working:
pane about +310 / +365 / +51, paired about +692 / +1479 / +48, the paired figure
including roughly 300 production lines for the `TabWidget` rewrite.

* Paired tabs give each page a real tab identity: commands, hints, status bar,
  sessions and undo need no routing, and devtools don't conflict.
* They rewrite the base of a central class and couple tab selection to pane
  focus. A latent bug of the rewrite (`tabopen()` showing background tabs)
  survived the original tests of the "behavior-neutral" first commit.
* The pane is far smaller and leaves `TabWidget` alone, at the price of the
  routing above and the second page not being a tab.

My recommendation is the pane first, and paired tabs only if upstream asks for
Chrome-style tab pairs.

== Tests

* Unit: `tests/unit/misc/test_miscwidgets.py` (pane mode and a randomized slot
  test), `tests/unit/browser/test_signalfilter.py`,
  `tests/unit/browser/test_browsertab.py` (`active_pane()`).
* End-to-end: `tests/end2end/features/split.feature`. Helper steps inspect real
  widgets (layout, status bar text, tab registry), not only the log.

Run headless with
`QT_QPA_PLATFORM=offscreen QTWEBENGINE_CHROMIUM_FLAGS="--no-sandbox --disable-gpu"`.
In end-to-end scenarios raw commands need full URLs (`http://localhost:(port)/...`,
otherwise the argument is searched), commands chained with `;;` take no leading
colon after the first, and URL based commands need the pane to have loaded first.

Manual smoke test (temporary profile, `--temp-basedir`):

. Open a page, `:vsplit <url>`; both pages show side by side. Drag the divider,
  resize the window.
. Click each page; `:open`, `:back`, `:yank`, scrolling and hints act on the
  clicked one, and the status bar follows.
. `:split-focus` both ways; run `:` commands and confirm focus returns to the
  page you were on.
. Switch to another tab and back; `:hsplit` to move the pane; `:split-close`.
. Close the tab with the pane open; try `:devtools`, `:tab-give`.

== Questions for upstream

* Is a second page inside a tab (pane) acceptable as a first version, or are
  paired tabs wanted?
* Command naming (`:vsplit`/`:hsplit` vs `:split` with options), and whether a
  pane should be persisted in sessions.
* Is sharing the inspector's slot acceptable, or should a pane coexist with the
  devtools?
