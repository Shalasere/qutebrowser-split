= Split view: paired tabs, implementation notes

Status: implemented on branch `feature/split-view-paired-tabs`, 2026-11-09.
Not submitted upstream, and no maintainer has commented on the design yet.
This is the first version of
https://github.com/qutebrowser/qutebrowser/issues/1716[issue #1716]: two
existing tabs of a window shown together. Read
link:split-view-research.asciidoc[the research note] for source links and
alternatives. Incorporate maintainer feedback before locking in the command
names.

== Behavior

`:vsplit [index]` and `:hsplit [index]` pair the current tab with another tab
of the same window (the tab at `index`, or a new tab with the current URL) and
show them left/right or top/bottom. `:split-focus` selects the other tab,
`:split-close` ends the split.

* Both tabs stay ordinary tabs: own tab bar entry, index, history, title,
  favicon. Commands, status bar, hints and key modes follow the *selected* tab.
  The tab bar highlight and the status bar are the only active-pane marker, and
  nothing in the tab bar says which tabs are paired.
* Selecting either tab shows the pair. Selecting any other tab shows that tab
  alone, and selecting a member again brings the pair back with its divider
  position.
* Clicking into the other half selects it.
* A tab belongs to at most one pair. A window can have several pairs.
* Pairs can be non-adjacent. Pinned tabs can't be paired.
* A page in full screen is shown alone while it is selected, and the pair comes
  back when it leaves full screen.
* Closing, moving (`:tab-move`, dragging) or pinning a member dissolves its
  pair. `:undo` re-opens the tab but doesn't restore the pair.
* Nothing is reloaded or reparented by any of this.
* `tabs.tabs_are_windows` makes `:vsplit` and `:hsplit` fail. A pair which
  exists when the setting is turned on stays until it is closed.
* Pairs are saved in sessions (`pairs` key per window).

== Architecture

`QTabWidget` shows one page of its internal stack, and a widget can't be in
that stack and in a `QSplitter`. `TabWidget` therefore is a plain `QWidget`
(`QBoxLayout` of `TabBar` and `ViewHost`) that keeps the camelCase API callers
use (`widget()`, `indexOf()`, `insertTab()`, `currentChanged`, ...) and owns the
tab list.

* `ViewHost` (`mainwindow/viewhost.py`) is a `QSplitter` which owns every tab
  widget permanently and only toggles visibility, so tabs are never
  reparented. `show_views()` shows at most two views and hides all other
  children; `show_pair()` adds orientation and ratio. Dragging the divider
  stores the ratio in the shown `ViewPair`.
* `TabWidget` owns the pairs (`_pairs`) and decides what is shown in
  `update_display()`: the current tab, plus its partner unless the current tab
  is in full screen. It runs on every change of the current tab.
* All mutations of the tab list happen in `insertTab()`, `removeTab()` and
  `_on_tab_moved()`, so dissolving a pair on close/move is done there. Pinning
  is the one outside event: `TabbedBrowser._on_pinned_changed()` calls
  `unpair()`. Whether a tab may be paired is decided in one place,
  `check_pairable()`; sessions and commands both go through it.
* `TabWidget._on_focus_changed()` (connected to `QApplication.focusChanged`)
  selects the partner of the current tab when focus moves into it.
* `TabbedBrowser` connects `cur_fullscreen_requested` to `update_display()`.
  `tabopen()` no longer calls `tab.show()`: `ViewHost` shows the current tab,
  and a stray `show()` on any other tab would put it into the layout.

=== Session format

[source,yaml]
----
windows:
- tabs: [...]        # unchanged
  pairs:             # only written if the window has pairs
  - tabs: [0, 2]     # saved positions, first is left/top
    orientation: left-right    # or top-bottom
    ratio: 0.5       # fraction of the space for the first tab
----

Invalid pairs are skipped and all tabs are kept; a ratio is clamped to
0.1-0.9. Sessions written by the code before this change load the same, and
the old code ignores the `pairs` key (both checked by loading real files).

== Decisions and trade-offs

Each entry is: what we chose, the strongest case against it, and why we still
think it is right, or what we are unsure about.

=== Replacing the page stack of `QTabWidget`

Against: `TabWidget` is on the path of every tab operation, and a conservative
maintainer will not want it rewritten for a feature.

For: a stack can't show two live existing tabs, and the alternatives either
reparent tabs (page state lives in the widget) or fake a stack. The rewrite is
behavior-neutral and is the first commit of the branch, so it can be reviewed
and landed alone. Callers keep the same method names. The existing
`tests/unit/{mainwindow,browser,misc,completion}` and the tabs, sessions,
private, hints, keyinput and backforward e2e suites pass, and a randomized run
(below) checks the layout for all four `tabs.position` values.

Unsure: features `QTabWidget` gave for free which nothing here uses today
(accessibility of the page stack, `QTabWidget` style selectors; none of the
shipped stylesheets use them).

=== A process-wide `focusChanged` handler selects tabs

Against: hidden global state, selection as a side effect of focus, and
programmatic `setFocus()` on the partner changes the selection (for example
`FullscreenNotification` focuses the page which went full screen).

For: the requirement is that a click selects the pane before any command runs.
The focus ends up in a child of the tab (the render widget), so a filter on the
tab doesn't see it, and `focusChanged` also covers keyboard traversal. The
handler is 8 lines, only reacts to the partner of the current tab, and costs
7 us per focus change without pairs (12 us with one; 100000 calls measured).
It can't loop, and two guards are load-bearing, each with a test that fails
without it: `ViewHost` focuses the current tab before hiding others (otherwise
Qt moves focus into the partner and the handler flips the selection), and the
partner must be visible (a hidden partner of a full-screen tab can still be
focused). The e2e click test fails with the connection removed.

Rejected: connecting only while a pair exists (saves 7 us, adds a
connect/disconnect state machine that must not go stale).

=== Selection and focus are coupled; commands follow the selected tab

Against: users may expect commands to follow the pane they last touched
without the tab bar moving.

For: "current tab" is assumed in `signalfilter`, the status bar, hints, modes
and 56 other places which read the current tab or index. Making it mean
anything else would be a much larger change than coupling it to focus.

=== Several pairs per window

Against: more state (a list), more policy, a larger test matrix, and it looks
like tab groups.

For: forbidding it needs an arbitrary error and a replacement policy, and the
single pair costs the same dissolution rules. It saves about 10 lines. The
ratio state exists mostly because of it: `QSplitter` keeps the divider position
across hide/show by itself (a test passes with `setSizes()` removed), but not
per pair.

Unsure: whether upstream wants one pair in the first PR anyway.

=== Non-adjacent pairs, and moving a member dissolves the pair

Against: Chromium keeps split tabs adjacent. With nothing marking paired tabs
in the tab bar, two tabs far apart are not discoverable. And the move rule is
arbitrary here: pairs refer to tabs, so nothing breaks if a member moves.

For: enforcing adjacency means reordering the user's tabs as a side effect
(and `:undo` indices, signals), which is more invasive. The move rule comes from
the original contract (dragging behaves like `:tab-move`), is one line
(`unpair()` in `_on_tab_moved()`), and is easy to flip.

Unsure: this is a product decision. If upstream wants no rule, delete the line
and one test. Dragging a member dissolves the pair without a message.

=== Pair state in `TabWidget`, not `TabbedBrowser`

Against: the lifecycle of tabs belongs to `TabbedBrowser`, and a widget class
now has model state.

For: `TabWidget` owns the tab list, so it is the only place that sees every
insert, remove and bar-driven move, including drags, in the right order
relative to `currentChanged`. In `TabbedBrowser` the move hook would have to
reach into the bar. A mutation test supports this: removing the dissolve in
`removeTab()` is caught by the randomized run within 14 steps, and with it
about 40000 steps in total (19500 of them on the final code, 2255 with a pair
present) found no stale pair. The pin hook is the only logic left in
`TabbedBrowser`.

=== Pairing rules in three places

The pinned rule used to look scattered. It now is `check_pairable()` (also used
by session loading, which sets pinned before pairs) plus the pin event hook:
creating a pair and keeping an invariant when state changes later are two
different moments. Dropping the rule entirely (pinned tabs are only a
tab-bar thing) would remove both and is technically fine; it is kept because
the contract asked for it.

=== `:vsplit` without index opens a copy of the current page

Against: it loads the URL a second time, which the first plan wanted to avoid.

For: the index form pairs existing tabs without loading anything, which is the
contract. The no-argument form is a convenience matching vim's `:vsplit`; a
blank tab would need a second command before it is useful. It is the easiest
thing to change.

=== Session format: positions and names

Against: positions break if another tool reorders `tabs`; strings duplicate Qt
enum names.

For: tab entries have no id, and every tool that reorders them also breaks the
`active` flag. Names are readable and independent of Qt. The loader is
tolerant (invalid pairs are skipped, at most one entry per two tabs is read):
with 100000 entries for the same tabs it took 63 s before that limit and
2 ms after.

=== New `miscmodels.window_tabs`

`tab_focus` completes the same list plus entries which are invalid for
`:vsplit`, and `tabs` completes across windows. `tab_focus` is now built on
`window_tabs`, so there is one copy.

=== Full screen from the other half

Only the *selected* tab's full-screen request is forwarded (same rule as for
background tabs, `cur_fullscreen_requested`). A request from the visible
partner leaves the layout alone until it is selected, then it is shown alone.
If one half is in full screen and the user selects the other, both show.
Fixing these would need a rule for who owns the window state; not done.

=== Would a smaller change be accepted more easily?

Measured against the base commit: production +598/-84 lines (about 300 are the
behavior-neutral `TabWidget`/`ViewHost` rewrite, about 300 are the feature),
tests +1051 lines, docs +48.

* No sessions: -51 production, -128 unit test, about -70 e2e lines.
* No ratio state: -26 production lines and a few tests, but then pairs share
  one divider position and sessions can't store it.
* One pair per window: about -10 lines.
* Adjacent-only would be larger, not smaller.

Leaving out sessions and ratio persistence would save about 75 production
lines (12%) and 250 test lines (24%), at the price of splits that vanish on
restart. They are kept because the research note lists persistence as part of
the first version. The cheap compromise is to submit in three steps: the
rewrite alone, then pairs and commands, then sessions.

== How it was attacked

All against QtWebEngine on the offscreen platform.

* Random command sequences in a real qutebrowser (`:vsplit`, `:hsplit` with
  and without index, `:split-close`, `:split-focus`, `:tab-close`, `:tab-move`,
  `:tab-pin`, `:undo`, `:tab-only`, `:tab-give`, `:tab-take`, `:tab-clone`,
  foreground/background `:open`, full screen of the current and the other
  half, `tabs.position`, `tabs.tabs_are_windows`, hide/minimize/restore of the
  window; some commands chained without returning to the event loop). After
  every step: every pair member is in its window and unpinned, no tab is in
  two pairs, exactly the current tab (and its partner) is visible, nothing is
  reparented, saved pairs reference valid positions; after event processing
  the visible tabs have a real size and don't overlap. The suite passed
  without a violation on the code before and after the simplification.
* Page-initiated `window.close()` of the selected and of the other half,
  renderer crash of each half, quitting with pairs open (exit code 0, no
  profile warnings).
* Object counts after creating and closing windows with pairs and 200
  pair/unpair/close cycles: tabs and `ViewPair` objects go back to the start.
* Load counts and parents recorded for all pages across pair, reorder,
  select, orient and unpair (the e2e scenario "doesn't reload or reparent
  pages").

== Known limitations and open questions

* No tab bar marker for paired tabs and no active-pane marker besides the tab
  bar highlight. A `{split}` title field would be a few lines, but it needs the
  titles refreshed when pairs change; not done.
* `:undo` doesn't restore a pair; dragging a member silently dissolves it.
* The divider is a thin default `QSplitter` handle (it is visible, but not
  styled with the colors settings).
* Only QtWebEngine was tested. QtWebKit is not installed here, and the unit
  tests use fake tabs. Only the offscreen platform was used: no real X11 or
  Wayland focus behavior, in particular the click-to-select path.
* Command names, `:vsplit` without index, and the move rule are proposals.
  Do not claim upstream approval before a maintainer gives it.
